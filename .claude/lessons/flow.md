# Lessons — flow/Orchestrator (Tier 1, projekt-lokal)

- 2026-07-13 (Konsolidierung F-003/F-008/F-011/F-012/F-015 → main, Orchestrator) — **Parallele Feature-Batches vergeben Spec-/Datenmodell-IDs (BR-###) unabhängig voneinander doppelt: BR-132 war zum Merge-Zeitpunkt DREIFACH vergeben** (S-018 `analysis_method.last_reviewed_at`, F-011 `depot_fill_dedup.client_order_id`, F-012 `strategy.cluster`-Gate). Auflösung beim Konsolidieren: der bereits in main gelandete Stand behält seine Nummern, die Feature-Seiten werden umnummeriert (hier: BR-134, BR-135) und ALLE Referenzen per `grep -rn 'BR-###'` über Code, Tests, Specs und Migrations-Docstrings nachgezogen. **Wurzel-Kur für die Fabrik:** ID-Vergabe (BR-/ADR-/C-Nummern) darf bei parallelen Feature-Branches nicht dezentral „nächste freie Nummer" sein — entweder reserviert der Drain je Feature einen Nummernblock, oder die Vergabe erfolgt nur auf main (Feature-Storys referenzieren bis zum Merge einen Platzhalter).

- 2026-07-13 (Konsolidierung, Orchestrator) — **Zwei parallele Features legten dieselben Tabellen an: F-011 (`36e7c473f4aa`) erzeugte `strategy`/`time_horizon` als leere „FK-Voraussetzungs-Platzhalter" für Position-FKs, F-012 (`ddaf9dcc6216`) dieselben Tabellen als echten Katalog mit Seed** — beim Zusammenführen kollidieren beide Migrationsketten (`table already exists`). Auflösung (nur sicher, solange KEINE der Migrationen je auf main/Produktion lief): Katalog-Migration gewinnt; aus der Platzhalter-Migration die `create_table`/`drop_table` der doppelten Tabellen entfernen und deren `down_revision` auf die Katalog-Migration umhängen, Modell-Platzhalter-Klassen durch die echten ersetzen, abhängige Tests auf das strengere Schema (NOT-NULL/FK) anpassen. **Präventiv:** Wenn eine Story eine leere Platzhalter-Tabelle anlegt, deren echte Implementierung in einem ANDEREN offenen Feature liegt, gehört ein `depends` auf jene Story bzw. eine explizite Absprache ins Board — der dba-Review sollte Platzhalter-Tabellen für fremde Feature-Scopes als Warnsignal flaggen.

- 2026-07-13 (Konsolidierung, Orchestrator) — **Jeder parallele Feature-Branch mit eigenen Migrationen erzeugt einen eigenen alembic-Head; beim Konsolidieren mehrerer Branches entstehen Multi-Head-Zustände, die `upgrade head` mehrdeutig machen.** Bewährtes Muster: `uv run alembic merge -m "…" <head1> <head2>` als Merge-Point; nachfolgende Feature-Migrationen per `down_revision` an den Merge-Point hängen (statt weiterer paralleler Äste). Nach JEDER Ketten-Änderung: Volldurchlauf gegen temporären `postgres:17-alpine`-Container (App verlangt `DB_HOST/DB_PORT/DB_NAME/DB_USER/DB_PASSWORD` — NICHT `DATABASE_URL`) inkl. Idempotenz-Zweitlauf, plus `alembic heads` = genau 1. Achtung: frisch generierte `alembic merge`-Revisionen tragen unbenutzte `op`/`sa`-Imports → `ruff check --fix` + `ruff format` direkt danach.

- 2026-07-13 (Konsolidierung, Orchestrator) — **models.py-Merge-Konflikte zwischen Branches, die an derselben Stelle GROSSE unterschiedliche Klassen-Blöcke anfügen, sind verschränkt** (git nimmt gemeinsame Zeilen wie `)` / `def __repr__` als Anker und verzahnt beide Blöcke) — naives „beide Seiten behalten" erzeugt syntaktisch kaputten Code mitten in Ausdrücken. Robustes Muster: ours-Datei als Basis nehmen (`git checkout --ours`), das theirs-Delta strukturell extrahieren (Import-Delta + Konstanten-Block + Klassen ab `class X` bis EOF aus `git show <branch>:<datei>`) und per Skript anfügen; danach `ast.parse`-Syntax-Gate + volle Testsuite. Bei Spec-Konflikten gilt: Feldnamen des GELANDETEN Codes gewinnen über konzeptionelle Spec-v2-Umbenennungen; die konzeptionelle Absicht als Präzisierungs-Klammer erhalten.

- 2026-07-13 (S-020-Wiederaufnahme nach Rechner-Neustart, Orchestrator) — **Ein durch Neustart abgebrochener /flow-Lauf hinterlässt: (a) uncommittete, teils fertige Arbeit im Story-Worktree, (b) stale In-Progress-Claims auf Feature-Branches ohne zugehörige Arbeit** (F-014/S-043: 2 Claim-Commits, 0 Code). Recovery: Worktree-Stand per Datei-mtimes datieren (letzter Testlauf = Abbruchzeitpunkt), coder mit explizitem „Bestand prüfen, NICHT reset/clean"-Auftrag fortsetzen lassen; stale Claim-Branches ersatzlos löschen, wenn ihr einziger Diff der Board-Claim ist und das main-Board die Story korrekt auf To Do führt. `gh pr merge` unmittelbar nach einem Force-Push schlägt mit „not mergeable" fehl, bis GitHub die Mergeability neu berechnet hat — kurz warten und `mergeStateStatus` pollen statt blind retryen.
