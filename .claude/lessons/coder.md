# Coder-Lessons (ki-investment)

- 2026-07-12 (S-005, ci-fix, cicd) — **Test-Fixtures dürfen keine echten Secret-Muster imitieren — der CI-Secret-Scan (gitleaks) kennt keinen Test-Kontext.** Ein Dummy-Key im Format `sk_live_…` in Tests löste nach dem Merge die Regel `stripe-access-token` aus → main rot, Fix-PR nötig (#9). Fixtures als offensichtlich fiktive Strings bauen (z.B. `dummy-fixture-secret-42`); matcht auch das noch eine Entropie-Heuristik (`generic-api-key` bei Variablennamen mit `key`/`secret`), gezielt `# gitleaks:allow` NUR an der betroffenen Zeile setzen — nie tests/ pauschal in `.gitleaks.toml` allowlisten. Idealerweise vor dem Landen lokal scannen: `docker run --rm -v "$PWD:/repo" ghcr.io/gitleaks/gitleaks:latest detect --source /repo --no-git`.

- 2026-07-12 (S-005, Iter.1, reviewer) — **Neue direkt importierte Third-Party-Library explizit in `pyproject.toml` deklarieren, auch wenn sie transitiv schon über ein anderes Framework verfügbar ist.** `app/contracts/dateneingang.py` + `app/adapters/sockets/base.py` importieren `pydantic` direkt (`from pydantic import BaseModel, ...`), aber `pydantic` steht nicht in `[project].dependencies` — es funktioniert nur, weil `fastapi` es transitiv mitzieht. Ändert sich künftig die FastAPI-Version/-Extras oder wird `fastapi` einmal entfernt, bricht der Import ohne Vorwarnung. Jede Datei, die eine Library direkt `import`iert, macht diese Library zu einer direkten Dependency — unabhängig davon, ob ein Scaffold-Default sie schon transitiv mitbringt.
- 2026-07-12 (S-004, Iter.2, dba) — **Platzhalter-Spalte für eine spätere AC (z.B. Versionierung) muss in `docs/data-model.md` explizit sagen, was sie NICHT löst — nicht nur wofür sie vorbereitet.** `category_weight.config_version` (AC10-Platzhalter, S-004) ist ein reiner Wert-Stempel auf einer Zeile, die NICHT Teil des Primärschlüssels ist (PK bleibt `asset_class_id, category_code`) — ein künftiges Hochzählen des Werts würde die Vorgänger-Gewichte in derselben Zeile überschreiben, nicht historisieren. Für AC10 („nachvollziehbar, welche Konfigurationsversion einer Analyse zugrunde lag") reicht dieses Feld allein strukturell nicht: die Folge-Story braucht entweder eine Historientabelle (Snapshot je Version) oder `config_version` als Teil des PK + einen „aktuell gültig"-Zeiger, plus eine Referenz von `analysis_result` auf die genutzte Version. Die data-model.md-Notiz zu einer Platzhalter-Spalte muss diesen Rest-Weg explizit benennen, sonst wirkt die Spalte fälschlich schon wie „AC10 vorbereitet/gelöst".
- 2026-07-12 (S-004, Iter.1, reviewer) — **Schema-Felder ausserhalb des Story-Scopes im selben Diff in `docs/data-model.md` nachziehen, sonst weglassen.** `CategoryWeight.config_version` wurde als Vorbereitung auf AC10 (Versionierung, eigene Folge-Story) eingeführt, ist aber in `docs/data-model.md` (DBA-bindendes Detailkonzept) an keiner Stelle dokumentiert — die Spalte existiert damit nur im Code, nicht im Source-of-Truth-Schema-Dokument. Entweder das Feld gehört (mit Begründung) in `docs/data-model.md` nachgezogen, oder es wird auf die AC10-Story verschoben, damit das Schema dort ohne Altlast aus einer vorweggenommenen Design-Entscheidung entworfen werden kann.
- 2026-07-12 (S-004, Iter.1, reviewer) — **Test-Datei-Header-„Covers"-Block muss ALLE im File vorkommenden `@trace`-ACs auflisten, nicht nur die primäre.** In `tests/db/test_category_weights_validation.py` deckte der Header nur „AC7" ab, obwohl ein Test (`test_category_codes_constant_has_exactly_5_entries`) mit `@trace anlageklassen-config#AC6` getaggt war. Nach jedem neuen/geänderten Test-Case den Header-Covers-Block gegen die tatsächlichen `@trace`-Tags im File abgleichen (Gegenstück zu `reviewer/R03`).
- 2026-07-12 (S-003, Iter.1, dba) — **`server_default` in Migration UND ORM-Modell synchron deklarieren.** Setzt eine alembic-Migration `server_default=...` auf einer Spalte (z.B. `sa.Column(..., server_default=sa.false())`), muss `mapped_column(...)` im SQLAlchemy-Modell denselben `server_default` tragen — nicht nur `default=...` (das ist rein Python-/ORM-seitig, für Alembic-Autogenerate/`alembic check` unsichtbar, alembic/A07+A09). Sonst entsteht eine Modell/DB-Drift, die `alembic check` mangels `compare_server_default=True` (nicht Default) nicht erkennt.
- 2026-07-12 (S-003, Iter.1, dba) — **Seed-Inserts ON-CONFLICT-fest bauen, wenn `docs/data-model.md` Idempotenz fordert.** `op.bulk_insert()` erzeugt eine reine INSERT-Anweisung ohne Konfliktbehandlung. Verlangt das Modell für eine Seed-Migration explizit „idempotent seedbar (ON CONFLICT DO NOTHING)", stattdessen `op.execute(sa.text("INSERT ... ON CONFLICT (...) DO NOTHING"))` verwenden — oder, falls bewusst darauf verzichtet wird (z.B. weil `alembic_version` Doppel-Apply ohnehin verhindert), die Abweichung im Migrations-Docstring explizit begründen statt sie stillschweigend zu übergehen.
- 2026-07-12 (S-003, Iter.1) — **Diff im zugewiesenen Worktree erzeugen, nicht im Haupt-Repo-Ordner.** Der Coder-Diff für S-003 (app/db/*, alembic.ini, tests/db/*, pyproject.toml/uv.lock) lag unkommittiert im geteilten Haupt-Checkout (`/Users/alex/Git/Studis-Softwareschmiede/ki-investment`) statt im für die Session vorgesehenen `.claude/worktrees/<session>`-Ordner. Risiko: `git reset`/`checkout`/`clean` einer anderen parallel laufenden Session im selben Hauptordner kann diese Änderungen kommentarlos löschen (siehe CLAUDE.md „Parallelbetrieb: mehrere Cloud-Sessions", dokumentiertes Vorfallmuster).
