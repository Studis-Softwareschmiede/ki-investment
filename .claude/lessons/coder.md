# Coder-Lessons (ki-investment)

- 2026-07-12 (S-013, Iter.1, reviewer) — **Ein Dict, das eine Vergleichs-/Originalquelle nur nach `quellen_id` indiziert, verliert Informationen, wenn eine Quelle mehrere Kennzahl-Typen liefert.** `app.adapters.llm.cross_check.pruefe_cross_check` nimmt `originalquellen: dict[str, Originalquelle]` entgegen (Key = `quellen_id`) und prüft NICHT, ob `Originalquelle.kennzahl_typ == fakt.kennzahl_typ` — bei einer realistischen Quelle mit mehreren Fakten (z.B. eine SEC-Filing-ID liefert KGV, Kurs UND Marktkapitalisierung) kann der falsche Originalwert für den Vergleich herangezogen werden, ohne dass ein Test das auffängt (alle Testfälle nutzen genau einen Fakt pro `quellen_id`). Trägt ein DTO ein zusammengesetztes Identitätsmerkmal (hier: `quellen_id` + `kennzahl_typ`), muss entweder der Dict-Key das volle Merkmal abbilden (`dict[tuple[str, str], ...]`) oder der Konsument nach dem Lookup explizit auf Übereinstimmung der übrigen Identitätsfelder prüfen (sonst: verwerfen).
- 2026-07-12 (S-013, Iter.1, reviewer) — **Neue Env-Variable aus `pydantic-settings`/`BaseSettings` zählt für das Secret-Sync-Gate genauso wie `os.environ[...]`.** `app/config.py` führt `TOLERANZ_CONFIG` als Feld einer `BaseSettings`-Klasse ein (implizites Env-Mapping über `SettingsConfigDict`), ohne dass `.env.example` einen (auch nur auskommentierten) Eintrag dafür bekommt. Jede neue `BaseSettings`-Feld-/Env-Bindung braucht denselben `.env.example`-Nachzug wie ein direktes `os.environ["X"]` — die Herkunft der Env-Bindung (explizit vs. über ein Settings-Framework) ändert nichts an der Pflicht aus `secrets-subsystem.md` §9.

- 2026-07-12 (S-006, Iter.2, dba) — **Ein in `docs/data-model.md` §8 explizit für eine M:N-Tabelle gelisteter Index ist Pflicht, auch wenn die Tabelle bereits einen zusammengesetzten PK trägt.** `data_source_asset_class` hat PK `(data_source_id, asset_class_id)` — dieser Composite-Index deckt Lookups mit führendem `data_source_id` ab, aber **nicht** Filter allein auf `asset_class_id` (führende PK-Spalte ist `data_source_id`). §8 der Doku listet für genau diese Tabelle trotzdem einen dedizierten `(asset_class_id)`-Index ("Quellen je Klasse, Datenquellen-Abfrage-Matching") — die Migration `ea80c97626ee` legt ihn nicht an. Bei M:N-Tabellen mit Composite-PK immer prüfen, ob §8 zusätzlich zur PK noch einen Einzelspalten-Index auf die nicht-führende Spalte verlangt, und diesen explizit per `op.create_index(...)` ergänzen (nicht davon ausgehen, dass der PK-Index dafür reicht).

- 2026-07-12 (S-005, ci-fix, cicd) — **Test-Fixtures dürfen keine echten Secret-Muster imitieren — der CI-Secret-Scan (gitleaks) kennt keinen Test-Kontext.** Ein Dummy-Key im Format `sk_live_…` in Tests löste nach dem Merge die Regel `stripe-access-token` aus → main rot, Fix-PR nötig (#9). Fixtures als offensichtlich fiktive Strings bauen (z.B. `dummy-fixture-secret-42`); matcht auch das noch eine Entropie-Heuristik (`generic-api-key` bei Variablennamen mit `key`/`secret`), gezielt `# gitleaks:allow` NUR an der betroffenen Zeile setzen — nie tests/ pauschal in `.gitleaks.toml` allowlisten. Idealerweise vor dem Landen lokal scannen: `docker run --rm -v "$PWD:/repo" ghcr.io/gitleaks/gitleaks:latest detect --source /repo --no-git`.

- 2026-07-12 (S-005, Iter.1, reviewer) — **Neue direkt importierte Third-Party-Library explizit in `pyproject.toml` deklarieren, auch wenn sie transitiv schon über ein anderes Framework verfügbar ist.** `app/contracts/dateneingang.py` + `app/adapters/sockets/base.py` importieren `pydantic` direkt (`from pydantic import BaseModel, ...`), aber `pydantic` steht nicht in `[project].dependencies` — es funktioniert nur, weil `fastapi` es transitiv mitzieht. Ändert sich künftig die FastAPI-Version/-Extras oder wird `fastapi` einmal entfernt, bricht der Import ohne Vorwarnung. Jede Datei, die eine Library direkt `import`iert, macht diese Library zu einer direkten Dependency — unabhängig davon, ob ein Scaffold-Default sie schon transitiv mitbringt.
- 2026-07-12 (S-004, Iter.2, dba) — **Platzhalter-Spalte für eine spätere AC (z.B. Versionierung) muss in `docs/data-model.md` explizit sagen, was sie NICHT löst — nicht nur wofür sie vorbereitet.** `category_weight.config_version` (AC10-Platzhalter, S-004) ist ein reiner Wert-Stempel auf einer Zeile, die NICHT Teil des Primärschlüssels ist (PK bleibt `asset_class_id, category_code`) — ein künftiges Hochzählen des Werts würde die Vorgänger-Gewichte in derselben Zeile überschreiben, nicht historisieren. Für AC10 („nachvollziehbar, welche Konfigurationsversion einer Analyse zugrunde lag") reicht dieses Feld allein strukturell nicht: die Folge-Story braucht entweder eine Historientabelle (Snapshot je Version) oder `config_version` als Teil des PK + einen „aktuell gültig"-Zeiger, plus eine Referenz von `analysis_result` auf die genutzte Version. Die data-model.md-Notiz zu einer Platzhalter-Spalte muss diesen Rest-Weg explizit benennen, sonst wirkt die Spalte fälschlich schon wie „AC10 vorbereitet/gelöst".
- 2026-07-12 (S-004, Iter.1, reviewer) — **Schema-Felder ausserhalb des Story-Scopes im selben Diff in `docs/data-model.md` nachziehen, sonst weglassen.** `CategoryWeight.config_version` wurde als Vorbereitung auf AC10 (Versionierung, eigene Folge-Story) eingeführt, ist aber in `docs/data-model.md` (DBA-bindendes Detailkonzept) an keiner Stelle dokumentiert — die Spalte existiert damit nur im Code, nicht im Source-of-Truth-Schema-Dokument. - 2026-07-12 (S-003, Iter.1, dba) — **`server_default` in Migration UND ORM-Modell synchron deklarieren.** Setzt eine alembic-Migration `server_default=...` auf einer Spalte (z.B. `sa.Column(..., server_default=sa.false())`), muss `mapped_column(...)` im SQLAlchemy-Modell denselben `server_default` tragen — nicht nur `default=...` (das ist rein Python-/ORM-seitig, für Alembic-Autogenerate/`alembic check` unsichtbar, alembic/A07+A09). Sonst entsteht eine Modell/DB-Drift, die `alembic check` mangels `compare_server_default=True` (nicht Default) nicht erkennt.
- 2026-07-12 (S-003, Iter.1, dba) — **Seed-Inserts ON-CONFLICT-fest bauen, wenn `docs/data-model.md` Idempotenz fordert.** `op.bulk_insert()` erzeugt eine reine INSERT-Anweisung ohne Konfliktbehandlung. Verlangt das Modell für eine Seed-Migration explizit „idempotent seedbar (ON CONFLICT DO NOTHING)", stattdessen `op.execute(sa.text("INSERT ... ON CONFLICT (...) DO NOTHING"))` verwenden — oder, falls bewusst darauf verzichtet wird (z.B. weil `alembic_version` Doppel-Apply ohnehin verhindert), die Abweichung im Migrations-Docstring explizit begründen statt sie stillschweigend zu übergehen.
