# Tester-Lessons (ki-investment)

- 2026-07-19 (S-070) — **In der `zsh` (macOS-Default-Shell dieser Umgebung) ist `status` eine reservierte/read-only Variable** (letzter Exit-Code) — eine `for`-Schleife, die ein Kommando-Ergebnis in eine Variable namens `status` schreibt (z. B. Poll-Loop auf `pg_isready`/Healthcheck-Text), schlägt mit `read-only variable: status` fehl, OHNE dass danach ein sichtbarer Fehler den restlichen Testlauf stoppt — die Schleife bricht nur beim ersten Iterationsversuch ab, wirkt aber im Log wie ein harmloser Nebenwarnung. Für Poll-/Healthcheck-Loops (Docker-Container-Bereitschaft, AC22-E2E-Smoke o. Ä.) NIE `status` als Schleifenvariable verwenden — neutrale Namen wie `pgstat`/`ready`/`hc` nutzen.

- 2026-07-13 (S-037) — **`alembic check` (Model-Drift-Gate) meldet bei nativen Postgres-RANGE-partitionierten Tabellen (`market_data_bronze`/`silver`/`gold`, seit S-022/S-024, vgl. coder.md-Lesson) dauerhaft Drift (`remove_table market_data_*_default`, `remove_index …`, FK-/Type-Diffs) — auch wenn der aktuelle Diff diese Tabellen gar nicht berührt.** Ursache: SQLAlchemy/Alembic-Autogenerate kennt die von Postgres automatisch erzeugten Partitions-Kindtabellen (`..._default`) nicht als ORM-Modell, vergleicht sie aber gegen die Live-DB — das ist ein bekanntes, strukturelles Limit nativer Deklarativ-Partitionierung, KEIN durch S-037 eingeführter Regressions-Fehler (verifiziert: `alembic downgrade` auf den Vor-S-037-Stand + erneuter `alembic check` zeigt exakt dieselben bronze/silver/gold-Drift-Einträge, keine strategy_cluster/strategy/time_horizon-Einträge). Bei rotem `alembic check` IMMER zuerst prüfen, ob ALLE gemeldeten Drift-Einträge ausschliesslich Tabellen/Spalten ausserhalb des aktuellen Diffs betreffen (Downgrade-Vergleich oder `git diff --stat` gegen die gemeldeten Tabellennamen) — nur bei Drift-Einträgen, die vom Diff berührte Tabellen/Modelle betreffen, ist es ein echter FAIL. `alembic upgrade head` (Apply) + `alembic current --check-heads` (Head-Konsistenz) bleiben davon unberührt grüne, verlässliche Gates.

- 2026-07-12 (S-051) — **`docker exec <container> psql ... <<'SQL'` (Heredoc ohne `-i`) liefert exit 0 UND komplett leeren Output — sieht wie ein leerer, aber "erfolgreicher" Lauf aus, ist aber ein stiller No-Op, weil `docker exec` ohne `-i` nicht an stdin des Containers angebunden wird und das Heredoc verwirft.** Für einen manuellen Live-Postgres-Smoke (Migration-Apply-Dispatch-Verifikation, z.B. `ON DELETE CASCADE`-Regressionscheck gegen echtes Postgres statt nur SQLite-Mock, siehe `agents/tester.md` §2b) IMMER `docker exec -i <container> psql ...` verwenden, wenn SQL per Heredoc über stdin gepiped wird — leerer Output bei Exit 0 ist kein Beleg für "nichts zu tun", sondern ein Hinweis auf eine fehlende `-i`-Flag, bevor daraus PASS abgeleitet wird.

- 2026-07-12 (S-023) — **`pytest 9.1.1` unterdrückt bei `-q`-Modus (via `addopts = "-q"` in `pyproject.toml`) und nicht-interaktivem Output (Pipe/Tool-Capture) die abschliessende `"N passed in X.XXs"`-Zusammenfassungszeile** — `uv run pytest -q` (und auch `-ra`) endet in dieser Umgebung nach dem `warnings summary`-Block ohne die gewohnte Summary-Zeile, obwohl Exit-Code `0` und alle Dots grün sind. Nicht fälschlich als unklares/fehlgeschlagenes Testergebnis werten: Exit-Code prüfen (`echo $?`) UND die Dot-Anzahl gegen `pytest --collect-only -q` (zeigt `"N tests collected"`) abgleichen, statt auf eine grep-bare `"passed"`-Zeile im Output zu vertrauen.

- 2026-07-12 (S-022) — **Manueller SQL-Smoke gegen einen inhaltsbasierten Dedupe-Trigger (Vergleich zweier Spalten wie `payload`+`observed_at`) darf `now()`/`NOW()` NICHT zweimal getrennt in aufeinanderfolgenden `INSERT`-Statements als "identischer Zeitstempel" annehmen** — jeder `now()`-Aufruf wird zum Zeitpunkt der jeweiligen Anweisung neu ausgewertet (hier ca. 11s Differenz durch Tipp-/Ausführungszeit zwischen zwei manuellen `docker exec psql`-Aufrufen), wodurch ein als "Duplikat" gedachter zweiter Insert vom Trigger korrekt als *abweichende* Revision durchgelassen wurde (Trigger funktionierte richtig — der Test war falsch aufgebaut, kein FAIL). Für einen echten Idempotenz-Smoke gegen so einen Trigger IMMER einen fixen, literalen Zeitstempel (z.B. `'2026-01-01T00:00:00+00:00'`) für die zu vergleichende Spalte in beiden Inserts verwenden, nie `now()` in getrennten Statements. Ebenso: Inserts gegen FK-pflichtige Spalten (`data_source_id`) mit real geseedeten IDs aus der Migration befüllen (`SELECT id FROM data_source LIMIT 1`), nicht mit frei erfundenen UUIDs — sonst FK- bzw. NOT-NULL-Fehler in Neben-Spalten (`frequenz_sekunden`) verschleiern das eigentliche Test-Ziel.

- 2026-07-12 (S-006) — **`docker-compose.yml` (db-postgres-Template) published den `db`-Service standardmässig NICHT auf einen Host-Port** — nur der interne Compose-Netz-Zugriff (Service-Name `db`) ist vorgesehen (Migrations-Container liest `DB_HOST=db`). Für einen lokalen Tester-Lauf von `alembic upgrade head` direkt via `uv run` (statt über den Migrations-Container) braucht es einen temporären Port-Publish, sonst `Connection refused` auf `localhost:5432`. Vorgehen: lokale `.env.db` (NIE committen) mit Test-Credentials anlegen, danach `docker compose -f docker-compose.yml -f <override-mit-ports-5432:5432>.yml up -d db` starten, auf `healthy` pollen (`docker inspect --format='{{.State.Health.Status}}' <container>`), Migration mit `POSTGRES_DB/POSTGRES_USER/POSTGRES_PASSWORD` + `DB_HOST=localhost DB_PORT=5432` env-Vars laufen lassen. Nach dem Lauf `docker compose down -v` + Override-Datei und `.env.db` wieder löschen (nicht Teil des Diffs).

- 2026-07-12 (S-012) — **`uv run ruff format --check .` (aus `knowledge/python.md` Test-Approach) kann pre-existing unformatierte Dateien aus früheren Stories melden, die vom aktuellen Diff nicht berührt sind** (`app/main.py`, eine Migration aus S-003) — kein Regressions-FAIL, aber im Handoff explizit als "pre-existing, nicht im Diff" vermerken statt stillschweigend zu ignorieren. `gitleaks` lokal fehlt oft (nicht installiert) → Docker-Fallback `docker run --rm -v "$PWD:/repo" ghcr.io/gitleaks/gitleaks:latest detect --source /repo --no-git` nutzen (siehe coder.md S-005-ci-fix-Lesson); `pip-audit` analog via `uvx pip-audit` statt `uv run pip-audit` (nicht als Projekt-Dependency installiert).
